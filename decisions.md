# Implementation Decisions

This log records decisions and tradeoffs made while implementing the documented phases. The repository documentation remains the source of truth; this file records implementation choices where the docs leave room for interpretation.

## 2026-10-05

- **Scope:** Implemented only Phase 0 and Phase 1. Hardware control, simulator orchestration, domain rules, telemetry streaming, persistence migrations, auth, and reports remain deferred to their documented phases.
- **Framework:** Chose Next.js App Router with strict TypeScript because it is the architecture document's specified application foundation and gives the shell a direct path to later route handlers and server actions.
- **Styling:** Added Tailwind/PostCSS configuration but kept the initial design system in a colocated global CSS token layer. This keeps the Phase 1 shell visually precise and easy to audit before extracting more primitives into a shadcn-style component library.
- **Visual direction:** Used the documented dark engineering palette, cyan primary signal, green health state, amber warning state, restrained borders, compact navigation, and tabular numeric typography. Avoided decorative gradients and generic SaaS patterns; the single atmospheric radial background is limited to the application frame.
- **Typography:** Used Space Grotesk for interface text and DM Mono for measurements, IDs, and status labels. This preserves the technical tone while keeping numeric telemetry scannable.
- **Default mode:** Simulation Mode is visible in the top status bar and in the simulator panel. The environment default is `SIMULATION`, and the shell explicitly states that physical commands are unavailable.
- **Interactivity:** Sidebar selection is local shell state only. Buttons are visual affordances for the future workflows and do not issue hardware commands or imply that a test has started.
- **Persistence bootstrap:** Added the PostgreSQL Prisma datasource and the first catalog/session models needed for the later data layer, plus a small seed script. No migration was generated because no database was available in this workspace and Phase 2 owns the complete schema.
- **Validation:** Added a Vitest smoke test for the simulation default so the development-mode boundary is executable before the simulator exists.
- **Lint cleanup:** Named the exported ESLint configuration array so the bootstrap passes without warnings under the repository's lint command.
- **Build root:** Explicitly set `outputFileTracingRoot` to the repository because the user's parent Desktop directory contains an unrelated lockfile that Next.js otherwise detects as the workspace root.
- **Dependency install:** The normal install was interrupted by a registry connection reset and a Windows Prisma postinstall lock. Completed installation with `npm install --ignore-scripts`, then ran `npm run db:generate` explicitly; this preserves reproducibility while avoiding the transient hook failure.
- **Runtime check:** Used `PORT=3000` through the PowerShell environment because forwarding `-p 3000` through the npm script was interpreted by Next.js as a project directory. The production server returned HTTP 200 and rendered the shell.
- **Generated output:** Ignored `.next` and `node_modules` in the flat ESLint config after the first production build exposed generated framework types to lint. Validation now covers authored source only.
- **Framework declarations:** Also excluded `next-env.d.ts`, which Next.js owns and intentionally generates with triple-slash references that are not authored application code.
- **UI redesign:** Replaced the generic dark card dashboard with a bench-ledger composition: graph-paper ground, graphite rail, numbered navigation, a dominant waveform surface, an adjacent simulation setup panel, and a test ledger. The product facts and Simulation Mode safety boundary remain unchanged; the visual identity is intentionally no longer a reference-site clone.
- **Redesign palette:** Chose instrument-paper, graphite, signal blue, safety orange, and inspection green. This gives operators a strong action color and keeps telemetry distinct from health and exception states without relying on neon dashboard styling.
- **Responsive tradeoff:** On mobile, navigation becomes a horizontally scrollable icon rail and the ledger remains horizontally scrollable so dense test columns do not collapse into unreadable cards. The scrollbar chrome is hidden to keep the compact rail visually clean.
- **Detector follow-up:** Removed the tiled graph-paper background after the design detector identified it as a generic generated-UI signature. The redesign now earns its instrument character through layout, rules, typography, and signal colors.
- **Navigation behavior:** Left-rail controls now update the selected workspace title, subtitle, context kicker, and accessible `aria-current` state. Full route-specific data views remain deferred; this keeps the shell interactive without inventing unfinished domain screens.
- **Route behavior:** Replaced local-only navigation state with real Next.js `Link` routes for Dashboard, Live Test, Test History, MCB Database, Reports, Analytics, Alerts, AI Inspector, and Device/ESP32. Each route currently reuses the shell while exposing its own URL and active context; full domain-specific screens remain phase-scoped.
- **Route data views:** Added distinct simulation-backed content for every route: pre-flight workflow and event timeline for Live Test; searchable session ledger for History; model/profile catalog for MCB Database; persisted report records; quality trend metrics; alert queue; evidence-based AI Inspector; and gateway/sensor health. Shared masthead and rail preserve operator orientation while the content changes with the architecture module.
- **Engineering parameters:** Added reusable metric matrices for the requested electrical efficiency, current-control quality, measurement accuracy, repeatability/reproducibility, throughput, and reliability/safety measurements. Live Test shows control and instrument confidence; Analytics shows the complete engineering scorecard; Device Health owns losses, component margin, uptime, and protection; Reports shows repeatability and operating capacity.
- **Metric provenance:** Values are explicitly labeled `SIMULATION DATA` and remain advisory demo telemetry. No parameter is presented as an accredited certification result, and no value controls hardware or overrides the deterministic rule engine.
